task-interleaving Domain Events 1.0.0
  • UNLICENSED
  • application/cloudevents+json
  • task-interleaving maintainers
  • task-interleaving@iqvo.example.com

Event catalog for the task-interleaving bounded context (WES subdomain): when a station completes a task, which open task nearby could the operator do next with the smallest detour (ADR 0001, ADR 0002). The output is an advisory hint, never an assignment.

Published. The StationTrip aggregate (one per station) raises InterleavingHintIssued when it issues a hint, InterleavingHintConsumed when the hinted station claims one of the candidates, and InterleavingHintExpired when an unclaimed hint reaches its expires_at; the InterleavingPolicy aggregate raises InterleavingPolicyDeclared. Only InterleavingHintIssued is on the integration topic warehouse.task-interleaving.events (fulfillment-execution reads it, ADR 0002). All four types are on the analytics topic warehouse.task-interleaving.analytics. Events are written through a transactional outbox: the aggregate row and its already-encoded events are written in ONE database transaction and a relay drains them to Kafka (at-least-once; the CloudEvents id is stored with the outbox row, so a retry republishes the same id). A superseded hint raises no event of its own: a consumer learns of it from the next InterleavingHintIssued of the same station.

Consumed (ADR 0003). TaskAvailable, TaskClaimed and TaskCompleted from fulfillment-execution (TaskAvailable and TaskClaimed are pending producer change P2: they do not exist on its integration topic yet, this context ships first and accepts them), and ZoneRegistered, LocationSlotRegistered, LocationSlotDecommissioned and LocationGeometryUpdated from facility-layout. Each feeds a durable local copy (modes FULFILLMENT_MODE and LAYOUT_MODE, default permissive; consumer groups from FULFILLMENT_CONSUMER_GROUP and LAYOUT_CONSUMER_GROUP). The consumed messages below are the producers' own contracts, decoded independently here and never imported.

Envelope (mandatory). CloudEvents 1.0, structured content mode, Kafka header content-type: application/cloudevents+json; charset=UTF-8. Optional W3C trace-context headers (traceparent, and tracestate / baggage when present) carry the trace of the writing request; consumers may extract them and must not require them. specversion, id, source (/warehouse/task-interleaving), type, subject, time, datacontenttype (application/json) and dataschema (urn:warehouse:task-interleaving:<events|analytics>:<EventName>:v1) are all required. Kafka key and subject = the station id for hint events and the site id for the policy event. Type = com.warehouse.wes.task-interleaving.<entity>.<EventName> where <entity> is the raising aggregate, lowercase, no separators: stationtrip or policy. data is snake_case, optional fields are omitted when unset and timestamps are RFC 3339 UTC. A breaking payload change is a new .v2 type, never a mutation.

Operations

  • SUB warehouse.task-interleaving.events

    This service's integration topic. Written by the outbox relay; key = station id; every message carries the CloudEvents content-type header (plus the optional W3C traceparent of the writing request). Only InterleavingHintIssued is published here: the hint table of fulfillment-execution is its consumer. Dispatch on the full type, ignore unknown types, dedupe on id.

    Receive interleaving hints.

    Subscribe to the hints. Route on the full type (com.warehouse.wes.task-interleaving.stationtrip.InterleavingHintIssued). A hint is advisory: use it only as a tie-break inside one priority band, ignore it once expires_at has passed, and fail open when it is absent.

    Operation IDreceiveInterleavingHints

    Available only on servers:

    • production
    • #stationtrip

    Accepts the following message:

    Interleaving hint issued

    A station completed a task and nearby open tasks were recommended.

    • application/cloudevents+json

    type = com.warehouse.wes.task-interleaving.stationtrip.InterleavingHintIssued, dataschema = urn:warehouse:task-interleaving:events:InterleavingHintIssued:v1; subject and Kafka key = the station id. The CloudEvents time is when the hint was issued. candidates is non-empty (an empty candidate set issues NO hint), ranked from 1 by detour_m ascending then task_id, at most the policy's max_candidates. The hint is valid until expires_at.

  • PUB warehouse.fulfillment.events

    fulfillment-execution's integration topic (key and subject = the task id). This service consumes TaskAvailable, TaskClaimed and TaskCompleted under a stable consumer group read from env FULFILLMENT_CONSUMER_GROUP when FULFILLMENT_MODE=kafka. Every other type on the topic is ignored.

    Consume task availability, claims and completions.

    TaskAvailable upserts a task into the local open-task pool and TaskClaimed removes it (pending producer change P2: neither is published on the integration topic yet). TaskCompleted (verified on fulfillment-execution's origin/develop) records the completion at the station: the position is the completed task's to_location read from the local pool copy, so a completion of a task this context never saw as available is ignored. The CloudEvents id claim and the effect commit in one transaction; the offset is committed afterwards (ADR 0003).

    Operation IDconsumeFulfillmentTaskEvents

    Available only on servers:

    • production
    • #consumed

    Accepts one of the following messages:

    • #0TaskAvailable (consumed, fulfillment-execution, pending producer change P2)

      A task entered or re-entered the open-task pool.

      • application/cloudevents+json

      PENDING PRODUCER CHANGE P2: not yet published by fulfillment-execution, this contract is pinned here so the consumer ships first and the producer matches it. type = com.warehouse.wes.fulfillment-execution.task.TaskAvailable, source /warehouse/fulfillment-execution, dataschema urn:warehouse:fulfillment-execution:events:TaskAvailable:v1. Subject and Kafka key = the task id. Raised whenever a task ENTERS or RE-ENTERS the pool (release, lease expiry); upsert it into the pool copy. from_location is where the operator must go first, to_location is where the operator ends (PICK: both the pick bin; RELOCATE and REPLENISH: source and destination bin; PACK, SLAM and REBIN: the station code). priority_band is an opaque string equal across tasks that fulfillment-execution orders as peers; this context stores it and never interprets it. A message with an unknown task_type is stored but is never a candidate.

  • PUB warehouse.facility.events

    facility-layout's integration topic. This service consumes ZoneRegistered (key zoneId), LocationSlotRegistered, LocationSlotDecommissioned and LocationGeometryUpdated (key locationCode) under a stable consumer group read from env LAYOUT_CONSUMER_GROUP when LAYOUT_MODE=kafka. Every other type is ignored.

    Consume zones, location slots and location geometry.

    The geometry copy is keyed by locationCode (LocationGeometryUpdated upserts a point); a location's site is found through its zoneId (LocationSlotRegistered) and that zone's siteCode (ZoneRegistered), joined at read time, so the events may arrive in any order. Decommissioning removes the location and is irreversible. A location without known geometry is never a candidate and never an origin: its distance is unknown, not zero.
