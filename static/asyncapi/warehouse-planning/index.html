warehouse-planning Domain Events 0.5.0
  • UNLICENSED
  • application/cloudevents+json
  • warehouse-planning maintainers
  • warehouse-planning@iqvo.example.com

Event catalog for the warehouse-planning bounded context (WES subdomain): can this warehouse process the demand assigned to it?

Published (Phase 4). The CapacityPlan aggregate raises four events, published to warehouse.warehouse-planning.events through a transactional outbox: the plan and its already-encoded events are written in ONE database transaction, and a relay drains them to Kafka (at-least-once; the CloudEvents id is persisted with the outbox row, so a retry republishes the same id -- consumers dedupe on it). Per plan: CapacityPlanCreated on creation; on publication CapacityPlanPublished, plus CapacityShortageDetected and BottleneckDetected only when the plan has a shortage. ProcessCapacityRegistered/ProcessCapacityChanged are NOT published yet.

Consumed (Phase 3). ShiftPlanCommitted (workforce-management) and LocationSlotRegistered/LocationSlotDecommissioned (facility-layout) keep local ProcessCapacity read models current; this context never makes a live cross-context call.

Consumed (ADR 0004, opt-in). OrderAllocated and OrderPartiallyAllocated (order-management, topic warehouse.order-management.events) keep a local expected-demand read model current when DEMAND_CONSUMER_GROUP is set (unset = no consumer). Each order is counted once, at its latest promise cutoff, and attributed to the ONE configured site (DEMAND_SITE_ID): order-management's events carry no fulfillment site. OrderRepromised and every other type are ignored.

Analytics stream (ADR 0005). The same four events are ALSO written to warehouse.warehouse-planning.analytics in the SAME outbox transaction (two outbox rows per event, one per topic), as CloudEvents 1.0 with the SAME type and the SAME id per occurrence but dataschema=urn:warehouse:warehouse-planning:analytics:<EventName>:v1. The integration messages are byte-identical to what they were before the stream existed. The analytics payloads are the integration payloads plus additive, analytics-only fields: today binding_constraint on CapacityPlanPublished (the constraint type -- LABOR, STATION, ... -- binding the bottleneck step; "" for a plan created before it was recorded). Only this service's own planning-projector consumes it (fixed consumer group, at-least-once, offsets committed after the projection committed), into a SEPARATE analytical database that planning-reports serves read-only. Poison messages go to warehouse.warehouse-planning.analytics.dlq.

Envelope (mandatory). Every message is a CloudEvents 1.0 event in structured content mode (Kafka value = JSON event format) with the Kafka header content-type: application/cloudevents+json; charset=UTF-8. All of specversion (1.0), id, source (/warehouse/warehouse-planning), type, subject, time, datacontenttype (application/json) and dataschema are required; the payload sits under data. No flat envelope, no toggle.

Type naming. com.warehouse.wes.warehouse-planning.<entity>.<EventName> where <entity> is the aggregate that raised the event, lowercase, no separators -- here capacityplan. dataschema = urn:warehouse:warehouse-planning:events:<EventName>:v1. subject and the Kafka message key = the capacity plan id (one plan's events stay ordered on one partition). A breaking payload change gets a new .v2 type and dataschema, never a mutation.

  • SUB warehouse.warehouse-planning.analytics

    This service's analytics topic (AnalyticsTopic in internal/adapters/outbound/kafka/analytics_encoder.go; ADR 0005). Written by the SAME outbox relay, from rows inserted in the same transaction as the integration rows; key = capacity plan id. Consumed ONLY by this service's planning-projector under a fixed consumer group read from env ANALYTICS_CONSUMER_GROUP (at-least-once; the offset is committed after the projection and the dedupe mark committed together in the analytical database). The projector dedupes on id, ignores unknown types, skips (with a rate-limited WARN) anything that is not CloudEvents 1.0, and dead-letters a known type with an unusable payload to warehouse.warehouse-planning.analytics.dlq (raw bytes plus x-dlq-* headers). Not an integration contract: other contexts consume the integration topic.

    order-management's integration topic (OrderTopic). This service consumes it with a STABLE consumer group read from env DEMAND_CONSUMER_GROUP (no default; unset means the consumer is not started). Only OrderAllocated and OrderPartiallyAllocated are acted on; every other CloudEvents type -- OrderRepromised included -- is ignored, and a message that is not a valid CloudEvent is skipped (WARN), never blocking the partition.

    Consume order-management's order allocation events.

    Consumed by this service into a LOCAL expected-demand read model (order_demand, one row per order id; GET /demand, get_expected_demand, and the default of POST /capacity-plans assigned_demand). An order is demand in a window [start, end) when its promise_date (the promise cutoff) is at or after start and strictly before end. Last writer wins per order id on the CloudEvents time (a later or equal time replaces, an older one is a no-op). The idempotency claim on the CloudEvents id and the upsert commit in ONE database transaction; the offset is committed only afterwards. order- management's events carry no site, no quantities and no cancellations (OrderCancelled is analytics-topic only), so demand is counted in ORDERS, attributed to the one configured site, and not netted; see docs/adr/0004-demand-ingestion-from-order-management.md.
