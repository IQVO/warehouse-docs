Fleet-wide strengths

  • Consistent hexagonal architecture: 37 Go applications, 0 domain/application imports of infrastructure (checked by AST on every file).
  • Small, simple functions: 21,757 production functions, average cyclomatic complexity 2.9, 0 above 15 (CI enforces cyclop 15 / gocognit 20).
  • Contract-first integration: 482 REST operations in OpenAPI, 270 published CloudEvents types in AsyncAPI, all events via a transactional outbox.
  • Layered test strategy: unit + 2,389 BDD scenarios + Testcontainers integration suites + 1,159 architecture fitness tests; mutation gates in 37 of 37 Go repos (median efficacy threshold 95%).
  • AI-ready by design: 159 MCP tools and 68 A2A skills expose read models to agents without bypassing the domain.
  • Decisions are written down: 690 Architecture Decision Records and 198 versioned database migrations (421 tables).

Fleet-wide risks and gaps

  • All REST and MCP endpoints are unauthenticated (authentication was deliberately removed fleet-wide); acceptable for a closed lab, a blocker for any exposed deployment.
  • Latest develop CI is red for returns-processing (integration job) and should be fixed before the next release.
  • 92 open code-scanning alerts and 252 open Dependabot alerts across the repos that run those scanners.
  • 21 repos have no code-scanning (CodeQL) analysis on record, mostly the newer Retail Network and Storefront services.
  • 23 repos have no published documentation site of their own; their context docs live only in this central site.
  • 42 production Go files exceed 500 lines; the largest use cases and consumers are the main refactoring candidates.

Cross-cutting API consistency

  • Idempotency: 143 of 209 REST write operations declare an Idempotency-Key in their contract; 18 applications key every write (mostly the Retail Network and Storefront contexts), while several older WMS/WES services key only some commands.
  • Versioning: 1 application versions its REST paths (network-inventory-planning); every other contract is unversioned, so a breaking change has no migration lane.
  • Event contracts: AsyncAPI is split 2.6.0 on 17, 3.0.0 on 18 repositories; CloudEvents type naming is uniform fleet-wide.
  • Agent surface: 159 MCP tools, 138 annotated read-only; 21 can change state (e.g. capacity-plan publication, pack-level retirement, work release) on an unauthenticated server.
  • Reviewers found small divergences that a shared API guideline would remove: replay header spelled Idempotent-Replayed vs Idempotency-Replayed, key reuse answered 422 in most services but 409 in one, command URLs mixing :verb, sub-path verbs and sub-resources, and unpaginated list endpoints in several services.

Architecture

Hexagonal DDD context; 5 binaries (facility API, projector, reports, MCP, A2A) + MF web remote; Postgres + outbox to Kafka

Strengths
  • Eight domain packages (site, zone, aisle, slot, structure, placement, travel, shared); travel is an infrastructure-free Dijkstra graph for shortest-path distance (internal/domain/travel/graph.go, ADR-0017).
  • RegisterLocationSlot enforces the Site -> Zone -> Aisle chain of custody and every PlacementRule before saving slot + LocationSlotRegistered atomically (usecases/register_location_slot.go:30-157).
  • Pure producer: publishes 15 event types and consumes none, so it is a stable upstream with no inbound coupling; analytics is a separate projector + reports binary pair.
  • Every resource-creating POST is wrapped by RequireIdempotencyKey (ADR-0019), with CORS deliberately allowing the header (internal/adapters/inbound/http/server.go:966-974).
Concerns
  • Slot registration reads duplicates, the parent chain and all placement rules before opening the unit of work (register_location_slot.go:102-142); a concurrent rule or zone change is not re-checked inside the transaction.
  • Rules.List loads every placement rule in the catalogue on each single-slot registration (register_location_slot.go:128) rather than the rules for the target zone; cost grows with the rule set.
  • All 38 REST operations are unauthenticated by fleet decision (ADR-0015 noted in server.go:971), including decommission and bulk layout import.

What was judged (hand review)

  • A reviewer read each repository’s README, core aggregates, use cases, one inbound and one outbound adapter, and its API specifications.
  • Architecture: boundary clarity, ports and adapters, aggregate invariants, integration style, resilience, deployability, observability.
  • Clean code: naming, size, complexity, duplication, error handling, depth of the test strategy.
  • API design: resource modelling, error model, idempotency and concurrency, pagination, versioning, event contract quality.
  • Scale: 3 = adequate, 4 = strong, 5 = exemplary with nothing material to fix. Every concern cites a file in the repository.
