part 1 · the business · why it exists

A delivery date is a promise, and the network exists to keep it

The retail network is the part of a retail business between a shopper's click and their doorstep. It tells the shopper an arrival date, takes the order, picks which fulfilment node ships it, moves the parcel through sortation, linehaul and last mile, tracks it, and measures every node against what it declared. The warehouse fleet is one vendor of this network, not part of it.

Today

Every context is built as a service on develop and wired into the reference cluster definition; the warehouse fleet plugs in as one vendor.

The catch

Only four contexts have an analytics read side, there are no report screens yet, and every REST and MCP endpoint is unauthenticated.

part 1 · the business · what is different

Dates come from real capacity, and the node is chosen late

Dates proven by a witness path

A quote exists only if a real route does: a node cutoff, departures with room, a wave with stops left. Fast tiers never use guessed times.

delivery-promise; ADR 0008, promise-model

Node chosen late, locked on accept

Sourcing keeps each group queued and may pick a different node than the promise, if the date still holds. The vendor's acceptance locks it.

order-sourcing; ADR 0002, ADR 0005

Declared, then measured

Nodes declare hours and cutoffs; node-performance grades them on facts, and the grade delays them or keeps them out of the fastest tiers.

node-performance; ADR 0003

Addresses live in two places

Ship-to addresses stay in customer-ordering and shipping-and-tracking. Events carry only a postal prefix; vendors get a label, never an address.

part 2 · architecture · the ground rules

Events, local read models and one owner per fact keep contexts independent

Events in, local read models

Contexts keep local copies of sibling facts fed by events; the promise makes no synchronous call.

One owner per fact

Topology owns nodes, linehaul owns departures, last mile owns waves; consumers conform and never write back.

Open Host Service everywhere

Each context publishes REST plus CloudEvents on its own topics; no shared database between contexts.

Outbox out, idempotent in

Every event leaves through a transactional outbox, and every consumer dedupes on the CloudEvents id.

A hard boundary to the fleet

No network context reads a warehouse topic; the only door is the Vendor API, and identifiers are mapped, never parsed.

node-topology: Supporting — The authoritative registry of the network's physical shape: every node (vendor fulfillment centres, cross-docks, returns centres, and the network's own sortation centres, delivery stations and air hubs), its declared operational profile, the directed lanes between nodes, the regions, and which delivery station serves which postal area. offer-availability: Supporting — Knows what the network can sell and from which node: the catalogue item, one listing per (catalogue item, node), and the quantity each node currently claims it can ship, with the basis the vendor gave for that number (physical stock or throughput-constrained). delivery-promise: Core — Tells a shopper, before and at purchase, the date a package will arrive, and makes that date true by construction: a delivery offer is quoted only from a feasible witness path (node cutoff, scheduled departures, delivery wave) that has remaining capacity, and a promise holds that capacity until the order is placed or the hold expires. customer-ordering: Generic — Turns a shopper's cart into a customer order: obtains a promise for every shipment group at checkout, records the order with the shopper and ship-to address (synthetic PII, held only here), shows status and tracking, and handles customer cancellation. order-sourcing: Core — Decides, as late as the promise allows, which node and path will actually fulfil each shipment group. vendor-connectivity: Supporting — The network's Open Host Service for vendors that operate fulfillment nodes. linehaul-transportation: Supporting — Runs the middle mile: turns lanes into scheduled departures (including a pickup departure at every vendor node cutoff), keeps each departure's remaining capacity, builds loads of packages onto departures, and reports when loads depart and arrive. last-mile-delivery: Supporting — Runs each delivery station: publishes delivery waves (induct cutoff, delivery window, stop capacity) that the promise relies on, plans routes for delivery service partners, and records every delivery attempt. shipping-and-tracking: Generic — Issues shipping labels (the only place outside customer-ordering that ever sees a ship-to address) and owns each package's journey: one customer-visible timeline consolidated from vendor handover, load and delivery facts, ending in delivered, returned or lost. node-performance: Supporting — Measures every node against what it declared and what was asked of it: acknowledgement latency, rejections, on-time handover against requiredShipBy, promise-kept rate and inventory feed freshness, over rolling windows, and grades the node. seller-inbound: Supporting — The seller-facing front door for stock coming into the network: sellers are onboarded and held to a compliance tier, inbound plans are confirmed, and shipments are labelled, shipped and received with discrepancies recorded.

part 2 · architecture · the decisions that shaped it

Domain decisions: separate promise from assignment, declare then measure, lock on acceptance

ADR 0002

Promise and order assignment are separate

Promising needs a fast local answer; assignment gains from waiting, so each gets its own model and owner.

ADR 0003

Capability is declared and measured

Nodes declare a profile, node-performance grades them from facts, and the promise applies the grade.

ADR 0005

The vendor's acceptance is the path lock

The network cannot see a vendor's floor, so a fill-or-kill acceptance is the moment the node stops changing.

ADR 0006

PII stays in two contexts

Only customer-ordering and shipping-and-tracking hold an address; the Vendor API returns a label and nothing else.

ADR 0007

CloudEvents namespace, no shared topic

A separate com.retailnetwork namespace stops a fleet consumer from subscribing to a network topic.

ADR 0008

Capacity is held at promise time

Fast tiers need a scheduled path; capacity is held per node cutoff and provisional holds expire with checkout.

No authentication anywhere

No mitigation on the roadmap yet: this one needs an owner.

Contract drift across event fan-in

→

Model-checked docs in CI, and a proposed fleet-level game day for exhausted capacity books.

Checkout needs a live promise call

→

Proposed: timeout budgets and a circuit breaker so checkout degrades predictably.
