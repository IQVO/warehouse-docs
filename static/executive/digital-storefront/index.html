part 1 · the business · why it exists

The storefront owns what a shopper sees and pays; the network owns what can be promised

The digital storefront is what a shopper sees and pays: search, a product page with a real delivery date priced per delivery tier, a cart, checkout and payment. It sits inside the retail-network organisation as its own domain. The network decides what can be promised and how it is fulfilled. The storefront never stores personal or card data, only a shopper id, an address id and payment tokens.

Today

Six bounded contexts, a Go edge service and a React web app are built on develop. All nine are in the k3s reference cluster's app registry.

The catch

Payments run against a simulator, there is no authentication anywhere, and nothing has carried a real shopper yet.

part 2 · architecture · the ground rules

Principles keep the contexts small, independent and checkable by tests

Own data, publish by outbox

Each context has its own Postgres. Events leave through a transactional outbox and consumers dedupe on the CloudEvents id.

Local read models, few calls

Data used in a decision is a local, event-fed copy. Synchronous calls exist only where a shopper's request needs an answer.

One edge with no domain model

The browser reaches only storefront-bff, which has no database and no Kafka. The web app talks to nothing else.

Rules as executable tests

Layering, no body logging, no card data and no call to restricted network routes are fitness tests that fail the build.

Translate at the borders

The payment provider sits behind a port, and checkout translates network terms. A swap changes one adapter, not the model.

product-content: Generic — Enriches the network's catalogue item with everything a product page needs and the item master does not have: description, bullets, attributes, media and the category tree. pricing: Core — Owns what a shopper pays: the list price and sale windows per catalogue item, the delivery charge per service tier, a synthetic tax table, and the binding, immutable, expiring PriceQuote a checkout session is confirmed against. product-discovery: Supporting — The read side of browsing and search: one ProductView per catalogue item (title, flags, content, categoryId, list and effective price, inStock, purchasable; the category path is joined from CategoryView at query time) and one CategoryView (tree plus purchasable counts), fed by events from offer-availability, product-content and pricing, searched with PostgreSQL full-text search and pg_trgm (D9), behind a port so a dedicated engine is a later adapter swap. shopping-cart: Supporting — Holds a shopper's intent: cart lines, the destination postal prefix, the delivery quote delivery-promise returned for the cart (per shipment group, with its offers and expiry), the shopper's tier selection per group, and a labelled, non-binding estimate (effective prices + selected tier charges + tax band) so the total cost is visible up front. checkout: Supporting — The purchase saga: one transaction across price, payment and the network's promise confirmation. customer-payments: Generic — Moves money with the shipment facts: authorize at checkout, capture each shipment group's allocation when it ships, release on cancellation, refund on lost or returned packages, re-authorize uncaptured allocations before the provider's authorization validity expires.

part 2 · architecture · the decisions that shaped it

The decisions behind the shape: in-org domain, no auth, saga payments, one edge

Storefront D1

The storefront is its own domain inside the network org

It may consume retailnetwork topics and open-host routes; the network never depends on it and no warehouse topic is touched.

Storefront D4

No authentication; guest-first flows

Matches the estate rule; sign-in is a synthetic shopper lookup by e-mail, and identity is deferred.

Storefront D5

Authorize before placing, capture per shipment group

Money follows shipment facts: release on cancel, refund on lost or returned packages.

Storefront D6

The storefront records the price; ordering stays price-free

Pricing and the binding quote live in the storefront, so the network's customer-ordering model is not changed.

Storefront D8; storefront-bff

React SSR web behind a Go BFF, the only edge

The browser reaches one service under /api/storefront, which holds no domain model, database or Kafka.

Storefront D9

Search is Postgres full-text behind a port

Good enough for the study, and the port lets a dedicated engine replace it as the catalogue grows.

part 2 · architecture · what could go wrong · and what we do about it

The risks that stand out: no auth, simulated payments, coupled checkout and stale views

No authentication anywhere

Every REST, MCP and A2A endpoint is open, and the cookie only holds state, not identity. Fine for a study, a gap beyond the cluster.

→

No mitigation on the roadmap yet: this one needs an owner.

Payments only meet a simulator

Partial captures, provider timeouts and reconciliation against real statements are unexercised in customer-payments.

→

Add a real provider adapter behind the existing port, plus a provider-statement reconciliation report.

Checkout is tightly coupled

It consumes no events and reads siblings synchronously, so an outage stalls buying; an in-doubt placement keeps a hold.

→

Load-test the PLACING lock and the in-doubt resolver under broker and provider latency.

Search views can go stale

product-discovery is wholly event-fed; a lagging consumer or dropped event leaves old product views until a rebuild.

→

Run the default-off rebuild Job as a scheduled drill; it snapshots the network reads, then replays events.
